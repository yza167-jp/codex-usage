# v1.9.0: durable / dot usage

Display update: v1.9.1 replaces the appended terminal section with a [unified
session inventory](v1.9.1-unified-sessions.md). The data scope, interfaces and
authentication rules described below are unchanged.

## Why these sessions were missing

The local report reads `sessions` and `archived_sessions` JSONL files. A dot
session can use the durable conversation backend while running tools on a local
Mac executor. Its appearance in the App, and its ability to run local commands,
do not imply that its conversation telemetry is persisted in those directories.

## Reading the report

`codex-usage cloud` discovers the signed-in account's durable inventory and
queries every returned thread separately. Both current and archived threads are
included; `--no-archived` limits discovery to current threads. A repeated
`--cloud-thread ID` selects exact IDs without listing the inventory.

`codex-usage 24h --cloud` appends the same lifetime Cloud section after the normal
local report. The selected period applies only to the local section. There is
no combined local-plus-Cloud period total because the available Cloud endpoint
does not return dated token deltas.

| Field | Meaning |
| --- | --- |
| WEEKLY % / 5H % | Backend lifetime usage relative to a full allowance; not necessarily usage in the currently active reset period |
| BALANCE CREDITS | Backend balance credits, separate from included-plan allowance and the local `CREDITS*` estimate |
| DATA | Backend `available`, `partial` or `unavailable` status |
| Data as of | Oldest backend freshness timestamp across batches, or unavailable if any batch lacks one |

The service may lag. A newly created or active thread can be listed while its
usage remains unavailable. Missing values are `—` in the table, `null` in JSON
and empty in CSV. Known zero values remain zero. No overall Cloud total is
computed from partially available rows. Descendants are queried as individual
threads when present in the inventory; no parent/child rollup is attempted.

JSON combined reports add a `cloud_usage` object without changing the local
`sessions` array. Combined CSV adds `host` and `scope`: local rows have
`selected_period`, Cloud rows have `lifetime`. Backend amounts have separate
column names from local estimates. Cloud-only JSON also retains model/effort/
speed groups as returned by the service.

## Interfaces and authentication

Verified against the installed App implementation and live read-only responses
on 2026-10-04:

- Durable inventory: authenticated WebSocket at
  `codex-cloud-backend.chatgpt.com`, using `initialize`, `initialized` and
  paginated `thread/list` requests only.
- Lifetime usage: HTTPS POST to
  `chatgpt.com/backend-api/wham/usage/thread_usage/query_v2`, with thread IDs,
  available creation timestamps and an empty descendant list for each thread.

These are App interfaces, not a promised public API. Errors fail explicitly;
they do not silently produce an empty successful report. Discovery is bounded
to 100 pages per archive state, usage queries to 50 threads per batch, and each
network request has a 20-second timeout. Repeated cursors fail rather than loop.
The WebSocket transport supports direct TLS and HTTP CONNECT proxies from the
standard proxy configuration.

Only explicit Cloud commands send network requests. They use the existing
`auth.json` access token and account ID, never print/persist credentials, reject
HTTP redirects, and do not refresh or rewrite login state. The App does not need
to run. An expired or inaccessible login must be renewed through Codex normally.
Cloud reports do not write token cache or quota calibration records.
